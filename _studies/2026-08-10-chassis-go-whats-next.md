# What's Next

## What This Is

chassis-go is the Go implementation of `chassis_suite`, a three-language ("chassis-go" / `chassis-py` / `chassis-ts`) microservice toolkit maintained by ai8future. It is explicitly a **toolkit, not a framework** (per `PRODUCT.md` and `README.md`): 25+ independently-importable packages across six tiers — foundation (config, logging, lifecycle, registry), transports (HTTP/gRPC middleware, resilient client), cross-cutting concerns (guards, feature flags, OTel observability, unified errors, Windmill-orchestration primitives), utilities (cache, crypto, webhooks, deploy conventions), event-bus integration (Kafka/Redpanda + Avro), and typed clients to shared platform services (entity registry, data lake, LLM inference, vector search, analytics). It serves other codebases, not end users: 112 separate `go.mod` files elsewhere in this machine's `_code` tree (across `ai_suite`, `crawl_suite`, `serp_suite`, `fabric_suite`, `infra_suite`, `search_suite`, and more) import `github.com/ai8future/chassis-go`, so this is real, load-bearing fleet infrastructure. Current version per `VERSION`: **11.3.26**, MIT licensed, Go 1.26.5 floor.

## Current State

**What actually works today:** every package documented in `README.md`/`PRODUCT.md` has a real implementation and tests — e.g. `idemkit` has 3 test files backing 1 source file. `TESTING.md` describes a genuinely mature five-tier testing regime (T0 deterministic unit through T4 hosted/credentialed), with opt-in **live** integration suites against pinned-digest Docker images for Redpanda, Qdrant, Meilisearch, an OpenTelemetry Collector, and an Inngest Dev Server (`testing/integration-suites.tsv`), each gated by a harness that hard-fails rather than silently skips. This is unusually rigorous for an internal toolkit.

**Maturity and velocity:** `CHANGELOG.md` contains 106 version headers running from `1.0.0` (2026-02-03, per `.planning/STATE.md`) to the current `11.3.26` — eleven major-version bumps in six months, most driven by version-gate/module-path discipline (`RequireMajor(N)`) rather than instability. A large share of recent entries are attributed to AI coding agents (`Codex:gpt-5.x`, `Claude:Opus`) running structured audit-and-remediation cycles; `_proposals/chassis-go-audit-remediation-plan.md` (2026-07-02) is one such cycle, and cross-referencing it against `CHANGELOG.md` (e.g. the posthogkit "Capture after Close" panic fix, line 272) confirms it was actually executed, not just planned.

**Newest and thinnest area — Windmill orchestration readiness:** `docs/windmill-orchestration.md` and the CHANGELOG's "Unreleased" section describe a "Wave 0" of packages — `authkit`, `idemkit`, `orchestration`, `conformance` — added to make chassis services callable and machine-checkable from a separate orchestration platform (`windmill_suite` elsewhere on this machine). Each of these packages is a single source file today. The code is explicit about its own limits: `conformance/conformance.go:193` emits the warning *"L3 checks are declaration-only in chassis core; verify durable outbox and event semantics in the owning service/addon tests"* — durable, event-ready guarantees are not implemented in core, and no `outboxkit`-equivalent exists yet in `chassis-go-addons` (which currently ships `pgkit`, `mailkit`, `dlkit`, `feedkit`, `rediskit`, `blob`, `ssrfcheck`). Similarly, `idemkit.NewMemoryStore` is documented in `docs/windmill-orchestration.md` as "process-local... suitable for tests, demos, and single-instance local services only" — a durable production store is explicitly deferred to service/addon code.

**Cross-language gap:** `_proposals/2026-07-28-chassis-ecosystem-semantic-parity-remediation-plan.md` (five days before this analysis) documents that chassis-go is effectively the most mature/reference implementation among the three chassis languages: Python's full-service Docker E2E is broken (binds to the wrong host), TypeScript's Kafka client is a stub capable of reporting false delivery/health success, and Problem Details shape, feature-flag hashing, and trace-ID precedence are all currently inconsistent across languages. That plan is "roadmap-ready" but explicitly blocked behind a not-yet-executed "G001 implementation-readiness gate" before any behavior changes land.

**Documentation drift:** `PRODUCT.md` states `**Version:** 11.3.8` while the actual `VERSION` file reads `11.3.26` — roughly 18 patch releases of drift in the document meant to be this repo's "product bible."

**Planning artifacts are historical, not active:** `.planning/PROJECT.md`, `ROADMAP.md`, `STATE.md`, `REQUIREMENTS.md`, and `FIX-PLAN.md` are a frozen snapshot of the original v0/v1 build (module path `v7`, "Phase 10 of 10 complete," dated 2026-02-03) — useful only as an origin story; the project has since gone through eleven more major versions and none of that material was updated. It should not be read as a live roadmap.

**Minor hygiene gaps observed directly:** two compiled Mach-O binaries (`02-service`, `04-full-service`, ~16MB and ~12MB) and a 201KB `coverage.out`, all dated mid-April, sit at the repo root — stale build artifacts that predate the entire Windmill-readiness push; `.gitignore` covers `*.exe`/`*.out`/`*.dylib` but not extensionless Go binaries like these. Separately, this working copy has no `.git` directory at all (`git rev-parse --is-inside-work-tree` fails), so I could not verify actual commit/push/branch state against `AGENTS.md`'s "auto-commit and push after every code change" policy from inside the repo.

## Product Opportunities

1. **Close the L3 "durable outbox" gap.** `conformance.go` itself flags L3 as declaration-only in core, and the sibling `windmill_suite` orchestration program treats a "chassis outbox" (dual-write correctness + Postgres-trigger surface) as one of its dozen or so foundational primitives. Chassis-go doesn't yet ship the piece that makes that real for Go services, and no existing addon covers it — this is a concrete, named, currently-empty slot.
2. **Harden Windmill readiness from "Wave 0" to production-grade.** `authkit`/`idemkit`/`orchestration`/`conformance` are each a single ~1-file package with a handful of tests, but are described (in `windmill_suite/VISION.md`, read for context) as the mechanism gating write-path safety across a much larger fleet. The in-memory idempotency store is explicitly test/demo-only; a durable, tenant-scoped store is the obvious next increment — though `PRODUCT.md`'s own rule ("chassis ships no DB drivers... belongs in a sibling repo") means this likely belongs in `chassis-go-addons`, not core.
3. **Act as the reference implementation for the cross-language parity program.** The July 28 remediation plan repeatedly names Go's OTel lifecycle and Windmill hardening as the reference Python and TypeScript need to catch up to; Go's own remaining task in that plan is comparatively small ("confirm current behavior against the full fixture set," G004/G006/G008). This is high-leverage because finishing it unblocks two other repos, not just this one.
4. **Fleet-operations tooling as a proof of the primitives chassis-go already emits.** Every consuming service already self-registers under `/tmp/chassis/<name>/`, heartbeats every 30s, and (once `kafkakit` is wired) emits lifecycle events — but nothing in the ecosystem currently productizes that data (a gap independently named in `chassis_suite/VISION.md`'s "Fleet as One Machine" theme). Not chassis-go code work per se, but a reference consumer of the registry contract would validate that the promise chassis-go makes to 112+ dependents is actually usable end to end.
5. **Reduce documentation/governance lag as adoption scales.** With `PRODUCT.md` already 18 patch releases behind `VERSION` and a release cadence of roughly one version every day or two, the "what does chassis-go promise right now" surface is harder to trust than the code itself. Folding a `PRODUCT.md`-freshness check into the existing VERSION/CHANGELOG release discipline would cost little given how disciplined that process already is elsewhere.
6. **Repo hygiene pass.** Stale multi-megabyte binaries and a stale coverage file sitting at repo root are trivial to fix but are avoidable noise in a repo this many other teams `go get`.

## Risks & Open Questions

- **No `.git` directory in this working copy.** I could not verify actual branch state, ahead/behind-origin status, or whether `AGENTS.md`'s "commit and push after every change" policy is being honored day to day — this analysis is based solely on file contents as checked out here, not repository history.
- **The most recent planning material is process/governance-focused, not feature-focused.** Both `_proposals` documents (2026-07-02 audit remediation, 2026-07-28 semantic parity) are AI-agent-authored rigor/correctness programs, not statements of new end-user-facing capability. If the actual strategic bet for chassis-go is "expand what services can do" rather than "make what exists more correct across languages," none of the current planning material speaks to that directly — the opportunities above are inferred from what has already been built (Windmill readiness, event bus, platform clients), not from a stated future feature list.
- **Whether governance/rigor is intentionally being prioritized over feature breadth** (a defensible choice at fleet scale, given 112+ dependents) or is inadvertently crowding out product movement is not something the repository alone can answer — worth confirming with whoever owns the `chassis_suite` roadmap.
- **Windmill-program urgency is external to this repo.** The newest chassis-go packages exist to serve a separate orchestration program (`windmill_suite`, referenced in this machine's global `.claude/CLAUDE.md` project instructions as governing "cross-codebase glue"), but chassis-go itself contains no evidence of how far that program's actual fleet adoption has progressed or how urgent the L3/durable-idempotency gap is to its timeline — that context lives in `windmill_ops/docs/`, outside this repository.
- **"Audit treadmill" risk.** Given roughly one release every day or two for six months, much of it AI-agent-driven audit-and-fix cycles on the agents' own prior work, there is a plausible risk of continuously finding and re-fixing issues introduced by the same process without independent confirmation that net reliability is improving for the 30+ consuming suites. Static analysis of this repo cannot confirm or rule this out.
- **Not an archive or dead project** — with 112 external `go.mod` references and multiple releases per week, chassis-go is unambiguously active and heavily depended upon; no "wind it down" framing applies here. The one boundary worth watching is scope creep on the "toolkit, not framework" principle: `authkit`/`idemkit`'s Windmill-specific middleware already reads closer to opinionated framework behavior than the rest of the toolkit, which `PRODUCT.md`'s own design rules explicitly warn against.
