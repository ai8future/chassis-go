# What's Next

## What This Is

`chassis-go-windmill-readiness` is a full standalone checkout of the `chassis-go` Go microservice toolkit — module `github.com/ai8future/chassis-go/v11`, pinned at `VERSION` **11.3.0**. Its `CHANGELOG.md` `[Unreleased]` section and `docs/windmill-orchestration.md` show it exists to carry the "Windmill orchestration readiness Wave 0" primitives (`authkit`, `idemkit`, `orchestration`, `conformance`) specified in `windmill_suite/windmill_ops/docs/chassis-go-windmill-orchestration-readiness.md`. It serves the same audience chassis-go itself serves — Go service developers across the ai8future fleet — but as a directory it is not consumed by anything: a repo-wide grep for `chassis-go-windmill-readiness` across `/Users/cliff/Desktop/_code` turns up no `go.mod` replace directive, no flow, no doc reference except one, discussed below.

## Current State

**What works today (verified):** `go build ./...` succeeds, and the five Windmill-relevant packages pass their tests (`go test ./authkit/... ./idemkit/... ./orchestration/... ./conformance/... ./tracekit/...` → all `ok`). The `[Unreleased]` CHANGELOG entry accurately describes the shipped code: `authkit` scoped inbound bearer auth, `idemkit` tenant-scoped HTTP idempotency (memory-store only), `orchestration` capability manifests, `conformance` L0-L2 runtime evidence plus declaration-only L3, a tightened `tracekit` trace-ID contract (`tr_[0-9a-f]{32}` canonical, bounded `tr_[0-9a-f]{12}` legacy), and extended `errors`/`call` retry classification. `testdata/windmill/contracts/` carries pinned cross-language contract fixtures (schemas, checksums, `PROVENANCE.md`) consistent with the BRIDGE A2/A10 amendments referenced in `windmill_ops/AGENTS.md`.

**The critical finding:** side-by-side diff against the actual mainline `chassis-go` (`chassis_suite/chassis-go`, `VERSION` **11.3.26**) shows this directory is a **stale, frozen fork** — its `idemkit/idemkit.go` last changed 2026-07-05; mainline's continued through 2026-07-13, -07-15, -07-22, and beyond. Concretely:

- Mainline's `idemkit` gained `LeaseToken`/`LeaseStore` (claim-ownership tokens preventing stale-owner ABA mutation after expiry/replacement), `DefaultMemoryCapacity`, `WithRequestBodyLimit`/`WithResponseBodyLimit`, and an explicit doc-comment admitting the middleware "cannot make a handler's business side effects exactly once by itself." This directory has none of it — it still carries the exact bugs mainline's own `_bugs_fixed/` documents as fixed on 2026-07-13: `idempotency-ambiguous-completion.md`, `idempotency-stale-lease-aba.md`, `idempotency-unbounded-capture.md`, `cancelled-idempotency-cleanup-stranded-claims.md`.
- Mainline has **50** files under `_bugs_fixed/`; this fork has **21**. Mainline's `CHANGELOG.md` is 1311 lines vs. this fork's 1139.
- Mainline added a G006 CI topology, a five-tier `TESTING.md` policy, machine-enforced coverage-floor gating, OTel telemetry redaction, `kafkakit.PublishKeyed`/`Ping`, and two newer strategic proposals (`_proposals/2026-07-28-chassis-ecosystem-semantic-parity-remediation-plan.md`, `_proposals/chassis-go-audit-remediation-plan.md`) — none of which exist here.
- The module path (`github.com/ai8future/chassis-go/v11`) is **identical** to mainline's, so this checkout cannot function as an independently versioned dependency; anything built against it would collide with the real module.

**`.planning/` is vestigial**, not current: `PROJECT.md`, `ROADMAP.md`, `REQUIREMENTS.md`, and `STATE.md` are all dated 2026-02-03 and describe the *original* 10-phase, v7-module-path MVP build (config/logz/lifecycle/testkit/httpkit/health/grpckit/call + examples) — four major versions and roughly 200 CHANGELOG entries before the Windmill work this repo is nominally about. It was never updated after the initial scaffold and should not be read as a roadmap for the code that's actually here.

**Maturity level:** feature-complete for a narrow, already-superseded slice of work (Wave 0), but operationally abandoned — not maintained, not consumed, indistinguishable from real `chassis-go` except by being three weeks older and less hardened.

## Product Opportunities

1. **Retire it.** It is an orphaned duplicate with an identical module path and zero consumers. The highest-value move is deletion or archival — it currently exists only as a trap: someone could import/build against the stale `idemkit` (missing ABA/lease protection and body-size limits) believing it's current, or waste effort "finishing" work already finished and hardened in mainline.
2. **If it was meant as a deliberate before/after audit artifact** (a frozen "Wave 0, pre-hardening" snapshot for comparison), formalize that intent: relocate it under a clearly archival path with a one-line README stating its purpose and pointing at mainline `chassis-go`, so its historical value survives without being mistaken for a live product.
3. **Redirect the underlying question to where it actually matters: adoption.** The proposal this repo implements (`windmill_ops/docs/chassis-go-windmill-orchestration-readiness.md`) names `delphi_api` or `user_svc` as the Wave-1 pilot to bring to conformance L2 and wire one real Windmill flow end-to-end. That pilot — not another copy of the toolkit — is the unproven half of "Windmill readiness." This repo's existence doesn't move that forward.
4. **One-time reconciliation diff before any deletion.** Confirm nothing unique lives only in this fork (my sampled diff found mainline strictly ahead everywhere checked — extra test files, extra hardening, no exclusive-to-fork logic — but a full-tree diff should confirm this holds beyond the sample).
5. **Close the loop chassis-docs already opened.** `chassis_suite/chassis-docs/WHATS_NEXT.md` (a sibling repo's own strategy doc) independently discovered this exact directory and explicitly flagged it as unresolved: *"Its exact relationship to chassis-go proper — staging fork, superseded experiment, or duplicated effort — is not resolvable from chassis-docs and wasn't investigated further."* This analysis resolves that question (superseded, frozen fork); feeding the answer back closes an open risk item logged elsewhere in the suite.

## Risks & Open Questions

- **Wrong-bet risk:** Any further engineering invested directly in this directory is close to strictly wasted — every improvement that would matter (idempotency ABA/lease safety, body-size limits, CI topology, coverage-floor enforcement) already exists, and is already better, in mainline `chassis-go`, three weeks ahead.
- **Not determinable from the code:** why this fork exists at all. Neither this directory nor mainline `chassis-go` is a git repository in this environment (`git status`/`git log` both fail with "not a git repository"), so there is no commit history or authorship trail to inspect. It could be an abandoned agent worktree, a deliberate pre-hardening audit snapshot, or accidental duplication — the file contents alone don't distinguish these.
- **Not determinable from the code:** whether any Windmill flow or pilot service has adopted these primitives from the *real* chassis-go. Surveying `windmill_suite/windmill_ops/flows` or consumer service repos was outside this task's scope.
- **Open question for the user:** was this snapshot deliberately preserved (e.g., a paused task, an A/B reference point) rather than deleted, or is it simply stray? That answer determines whether "delete" or "archive with a pointer" is the right call — the analysis here can't distinguish intentional preservation from oversight.
- **Compounding risk if left as-is:** because the module path is identical to mainline's, any future monorepo-wide tooling (a dependency audit, a `go build ./...` sweep across `chassis_suite/`) will see two divergent copies of "the same" module and may produce contradictory or misleading results without knowing one is a frozen historical snapshot.
